# Device support and exclusive operations

The product supports extensible device families. NW-A916/A918/A919 are the current discovery profiles, not a product-wide model constraint. `src/devices.rs` owns family IDs, USB matches, candidate model lists and references to shared firmware profiles. A USB match identifies a candidate family only. Never infer an exact model, media-format compatibility or permission to flash from a shared VID/PID, volume label or product string.

The existing `protocol`/`database` implementation is the OMGAUDIO media adapter. Future devices using another storage/database protocol need another adapter and explicit dispatch after verified identification; do not silently route them into OMGAUDIO. Package parsers and fixed vendor commands remain protocol-specific. Registering a family is not evidence that these protocols apply. The A91x UPG parser remains intentionally restricted to its researched format. NW-A916, NW-A918 and NW-A919 share one firmware profile (`sony-a910-upg`) and package signature. Compatibility is determined by that shared profile, not by the models represented in test fixtures. The existing offline transaction fixtures originated from A918; this is evidence provenance, not an A918-only compatibility rule. No model has live firmware-write permission. Exact model and serial identity must still match when reconnecting to a transaction, even between models sharing firmware.

`device_operation::acquire` provides a nonblocking OS file lock shared by application instances on the same host/user temporary directory. Music transfer entry, resume/recovery and legacy staged writes hold its RAII guard for their entire operation. Firmware USB inventory and fixed Windows read-only device queries use the same lock. Disk-app installation also participates. Local firmware file inspection needs no hardware lock.

Any future firmware upload/activation executor must acquire this guard before hardware access and retain it through activation, reconnect, readback and cleanup, including errors. Never gate this only on a disabled frontend button. Do not call a second guarded entry while holding the guard. Offline `firmware::session::Session` is a pure state model, not an executor.

Until volume and USB identities can be correlated reliably, the lock conservatively serializes operations across all devices. It does not coordinate unrelated software, another operating-system user or host. A paused music operation releases the live guard; its existing durable journal and recovery checks still apply. An unresolved firmware activation must be reconciled before any future executor allows other device writes, including after a process restart. Live flashing remains disabled until that recovery policy and hardware transport are implemented and validated.

Custom distribution identity and its current implementation limits are specified in [FIRMWARE_IDENTITY.md](FIRMWARE_IDENTITY.md). Firmware compatibility, installed build identity and hardware validation remain separate facts.
